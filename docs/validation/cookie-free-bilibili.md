# Bilibili 严格匿名验证记录

## 当前结论

2026-10-31，正式 C# 适配器在不发送 Cookie、不复用 Set-Cookie、不生成游客或设备指纹时，完成六类输入的解析：两个普通 BV（包含约 9 分钟样本）、同稿 AV 别名、用户提供的 b23.tv 短链、同一多 P 作品的第 1 P 和第 2 P。仓库外独立客户端只用适配器返回的 url + headers 完整下载六份 MP4，字节数与 API/CDN 响应头一致，每份均通过原生首个视频帧和音频样本解码，并核对完整文件时长；不宣称逐帧解码全部内容。

BV/AV 别名文件的 SHA-256 一致，两个不同 P 的文件哈希不同，所选 P 的时长与返回候选对应。上游毫秒时长与 MP4 封装时长存在最多约 9ms 差异；原生核对按实际视频的一帧加 1ms 封装精度判断，六份均通过。服务端没有下载媒体正文以补齐这些字段。

本实现的 Bilibili 已通过视频可行性门槛，注册为 bilibili；video 为 supported，imageAlbum/livePhoto/mixedAlbum 为 unsupported。正式 API、最终 Linux 容器及调用方独立下载验收均已通过，见后文。范围只包括普通 UGC 的所选单个分 P，不保证全部公开视频、网络或未来协议持续可用。

[脱敏成功统计](2026-10-31-bilibili-success.json)只含类别、状态与结构统计。真实输入、BV/AID/CID、完整地址、签名查询和原始响应只保存在仓库外，测试全部使用合成数据。

## 已选匿名链路

1. 分享文本通过既有提取器和平台注册表选择；b23.tv 手动跳转，不复用任何 Set-Cookie。
2. 第一方 `/x/web-interface/view` 返回匹配的 BV/AID、pages 和选定 CID。AV 经可信响应规范化，缺省第 1 P，显式 p 越界或无效时失败，不批量解析。
3. 第一方 `/x/player/playurl` 使用 BV、选定 CID、固定 fnval=1、fnver=0、platform=html5、fourk=0、qn=80、high_quality=1。实测未要求 Cookie、签名或指纹；请求 qn=80 不代表 1080P，样本实际响应 quality=64。
4. 只接受明确的单段 MP4，包含现存的 mp4720 与 hdmp4 格式标识。只返回上游实际提供的主/备用 URL，不重写 upos 主机。连续分段、DASH、FLV/HLS、权益预览或明显截短明确失败。
5. 当前验证的媒体根为 bilivideo.com；Bilibili 平台/API 主机与 CDN 权限和抖音隔离。API/播放地址不是最终 CDN；未知域名不自动放行。

未签名入口被拒绝时可有界尝试第一方 WBI 路径，公开 nav 参数与本地确定性算法不包含身份。固定合成向量覆盖编码/排序/时间，真实 TCP 替身核对 Query 字节不被二次编码；公开键仅在进程内短期复用，明确签名失效时最多刷新一次。不会以 Cookie、buvid、dm_img、浏览器或第三方解析恢复访问。

## 网络与资源边界

2026-10-31 初次验收时，本机 TUN 对 Bilibili 的系统解析返回 Fake-IP，默认容器即使指定普通 DNS 也得到合成地址。正式策略正确拒绝这些地址；该轮适配器诊断使用仓库外的真实公网 DNS，并继续通过同一个完整 IPv4/IPv6 分类器和固定连接 IP/TLS 主机校验。没有修改宿主网络或放宽目标策略。

容器阶段使用临时、隔离网络内的真实 DNS 服务，客户端仍通过普通系统 DNS 获得公网目标，再执行完整生产校验；该 DNS 服务仅用于验收，不是项目运行依赖，不将 DNS/hosts 映射作为生产配置。验收已删除临时 DNS 容器和隔离网络；宿主网络未修改。

元数据最多读取 2 MiB 解压后正文；每次重定向最多 5 跳；媒体仅响应头，禁用排空正文。一个列表最多尝试 16 个候选，成功最多返回 2 个；同一解析总时限覆盖短链、公开键、详情、播放和 CDN。

候选尺寸未知时保持 null，不把原稿尺寸或画质标签套用到低画质文件；过期语义未确认时为 null。调用方必须带每个来源自己的 headers；遇到失效后重新解析，不将地址永久缓存。

## 正式 API、CLI 与 Linux 容器

- 最终镜像的统一与指定平台两个 POST 入口均通过；六类 Bilibili 输入全部返回 200，用户提供的短链同时验证两个入口。
- 独立客户端再次仅使用正式 API 返回的 url + headers 完整读取六份文件；每份字节数匹配返回大小及 CDN Content-Length，SHA-256 与此前通过原生画面/音轨/时长核对的对应文件一致。
- 平台发现包含两个已启用平台，Bilibili 仅 video 为 supported；入站 Cookie、额外 JSON 字段仍拒绝，指定平台不匹配仍返回 PLATFORM_MISMATCH。
- 同一镜像中的抖音四类真实回归均为 200：视频 1 项、普通图集 12 项、实况图集 1 项、混合图集 4 项。
- Linux 镜像以 UID 1654 非 root 运行，只读根文件系统与临时 /tmp；docker diff 无持久化变更，服务未增加数据库、媒体卷、FFmpeg、浏览器或身份服务。
- CLI 使用 `--platform bilibili`，不写 --entry 时默认 adapter，六份仓库外输入全部通过，报告不包含作品标识、完整 URL 或签名 Query；不支持的入口和图集类别返回参数错误。

CLI 重复观察中有一次上游返回的 CDN 为 503，程序按预期报告 UPSTREAM_UNAVAILABLE；新的解析恢复成功。此现象保留为暂时可用性限制，未修改 CDN 主机、绕过安全策略或增加身份回退，不能将这些样本的成功理解为全网或永久可用保证。

## 2026-11-01 本机验收与归档补记

本机 dotnet / IDE 的后续排障复现了系统 Fake-IP 在详情请求连接前被目标策略拒绝、再经 HttpRequestException 映射为 UPSTREAM_UNAVAILABLE / 503 的行为。同一公开样本使用真实公网 DNS 对照时，详情、播放及 CDN 响应头验证均为 200，未发送 Cookie。用户随后将 bilibili.com、b23.tv、bilivideo.com 及其子域名加入 Fake-IP 排除范围，并确认本机 Postman 请求成功；没有放宽公网 IP 校验。这是新增解析与环境观察，不计作新增完整媒体下载样本。

归档前重新通过 742 项测试、格式检查及规格严格校验；25/25 项任务完成，主规格已同步，提案已[归档](../../openspec/changes/archive/2026-11-01-add-cookie-free-bilibili-resolution/proposal.md)。真实分享文本、标识和完整地址继续只在仓库外使用。

控制台日志的 Scope 输出和本地安全拒绝的错误分类细化仍可后续单独改进，本次归档保持现有运行行为；它们不扩展为本提案新增平台支持的未完成任务。
